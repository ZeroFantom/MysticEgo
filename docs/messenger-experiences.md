# Messenger experiences — Зеркало души и Духовные круги

Design extension to [Epic #118](https://github.com/ZeroFantom/MysticEgo/issues/118). User requirements: Telegram Mini App, VK keyboards, interesting group/community experiences. This document records proposed mechanics and implementation order, not deployed functionality. Names and individual mechanics below are design proposals.

## Shared rules

All channels use existing Mystic Ego account, active embodiment, permissions, canonical game events and world state. OAuth login and bot link remain independent. Private spiritual contact requires same in-game area; confirmed player friends may communicate across areas within the same world. Chat membership, Mini App context, real-world location, guild membership or moderator role never grant a bypass. NPCs perceive spiritual communication from an in-world identity, not a platform. Unknown world state fails closed. Do not add separate economy, inventory, NPC memory, character creation, quests or game state per platform.

## A. Telegram Mini App: Зеркало души

Start with a responsive web route inside the shared frontend, reusing accessible UI components and read-only world views. Launch from configured bot menu/profile or official direct link. Text bot remains a first-class fallback.
- MVP: account link status, active embodiment, current area, permitted contacts, friends, private spiritual dialogue, canonical history and unread state.
- Subsequent: read-only soul progression, inventory, quests, public chronicles, guild membership and event participation. Mutations use existing domain services and explicit confirmation; never add simulated local state that is treated as authoritative.
- Use theme, viewport, safe-area, back button and reduced motion; load lightweight assets, no AR/camera permission by default. Mobile app handoff remains presentation only.

Authentication: send raw Telegram WebApp initData over HTTPS POST to a dedicated endpoint. Validate official HMAC algorithm using the configured bot token on the server (reject duplicate/malformed fields, constant-time hash, bounded size and auth_date, bot-specific namespace). Never trust initDataUnsafe, query parameters, username, or the client-supplied user/peer/world. Resolve verified private Telegram user in bot realm; unlinked users see linking instructions only. A group-launched Mini App has no access to the group's conversation history and must not treat chat context as membership authorization. Replay-protect initial exchange; issue a short-lived restricted Mini App session, recheck active account/bot binding and server permissions per request, do not issue privileged Auth JWT or refresh tokens from initData. Don't embed OAuth secrets or link codes in URLs. Full account linking/management stays in trusted browser flow with recent password. Revocation denies subsequent calls. No persistent storage for initData or tokens. Verify actual clients, platform signature fixtures and isolated HTTPS staging first.
Official: https://core.telegram.org/bots/webapps (launch methods, validating data).

## B. VK keyboard interface

Keep text commands as fallback and use a shared action/view model rather than a second game engine.
- Persistent menu: Моя душа | Духовная связь; Друзья | Задания; Инвентарь | Хроники. First increment only show actions actually supported by backend.
- Contextual inline keyboards: permitted nearby entities, friends, back/next page, select a contact, start/leave a dialogue, accept/decline event invite. Free text goes to selected recipient only after fresh permission/world check; selection expires or invalidates on movement.
- Use VK keyboard JSON with callback actions; process message_event under verified Callback API secret and exact community. Acknowledge via messages.sendMessageEventAnswer where appropriate. Bind opaque action handle to provider/bot, actual sender, peer, purpose, scope and expiry; atomic consumption for mutations; dedup by event and action, check current account/role/world state. Never trust raw payload as game command or accept a private keyboard action from group context. Handle outdated controls with a refresh message. Group keyboards have a separate action namespace.
- Keep keyboard labels short, pages bounded, support old clients through explicit text fallback, and escape display names/control characters.
Official schema: https://github.com/VKCOM/vk-api-schema and https://github.com/VKCOM/api-schema-typescript/blob/master/src/methods/messages.ts.

## C. Духовные круги — shared community surfaces

Separate group/community adapter, not an extension of private message ingestion. Proposed experiences:
1. Общий костёр: an opt-in public gathering board, recruiting parties, sharing explicitly public rumors, cooperative travel preparation and event announcements. Group conversation itself stays out of NPC memory.
2. Представительство гильдии: link a verified chat/community to a real game guild with consent of both platform admin and authorized game guild officer; show public guild board, join requests, approved recruitment, shared goals. No automatic guild join from membership.
3. Эхо мира: server-published public world events, anomalies, wars, discoveries, faction notices, opt-in digests. Publish only explicitly approved public event projection, no hidden locations, private character state, quests or account IDs.
4. Collective encounters: e.g. a forest rift, rescue expedition, puzzle, resource drive, town defense. One canonical event across Telegram, VK and client; groups see public cards with progress, join/details buttons and outcome. Each participant explicitly joins using linked account; capacity, eligibility, time and action checked by game server. Remote player may register interest where allowed, but local participation requires current authoritative placement. No travel, NPC access, rewards or votes solely from external chat presence.
5. In-world public NPC appearances: only game-authored event projection or expressly permitted public scene; NPC addresses the eligible participants as in-world audience. Private NPC dialogue stays private; public scenes do not bypass area and consent rules. Nonplayers can see public lore/rules and a link to join Mystic Ego, never act as another player.
6. Community-specific reputation/chronicle is a projection of canonical verified achievements, not an independent XP source. Optional group votes affect only explicitly defined cooperative event choices, one eligible character/account per choice, server deadlines and deterministic resolution; no reward farming via repeated messages or inviting bots.

Group onboarding and safety:
- Default disabled. Verify bot membership and administrator authority via provider API, explicit owner approval for binding, per-chat capability flags (announcements, recruiting, events, votes, approved public scenes), guild/area mapping from trusted world data only. Record audit, allow pause/remove, revoke on lost authority/bot removal. Never need broad group history permissions; process explicit commands, mentions and action callbacks only. No automatic ingestion of ordinary chat messages or adding to model prompts.
- Group /link or private account command only directs to private chat; do not stage codes, expose account links or read private inventory/history in shared chat. Private answers via authenticated private channel, no fallback to group. No linking or password collection in group.
- Separate public event DTOs and private game DTOs; filter before enqueue and again before delivery. No cross-posting private conversations, social user IDs, tokens, account IDs, physical locations, hidden NPC or unapproved profile. Explicit opt-in for shared game name, otherwise no public player identity. Block/mute, reporting, admin moderation and per-chat/user/bot quotas. Quiet hours/digests optional. No unsolicited DMs, mass mentions or repeated announcements by default.
- Distinguish Telegram chat/thread and VK peer/community; verified membership/roles, event identity, callback scope and current game participation on each action. Group membership does not equal an in-world location or entitlement. Provider group updates dedup separately from private receipts; no changes to existing private-only parser until dedicated adapter is implemented.
- One world event ID and idempotent participant/action keys across all channels. Durable public outbox, per-destination delivery state, bounded retries and explicit uncertainty for non-idempotent provider sends; no duplicate rewards or duplicate state transitions. No rewards from raw vote counts.
- Example: forest rift is published to subscribed groups. Players click join, get a private eligible session and select their own character. World records reservation/attendance separately; only players actually present and eligible can perform the local event actions. Server computes the result once and publishes a public outcome. All three clients see the same canonical outcome.

## Implementation sequence and release gates

1. Finish existing authenticated Auth–Orchestra handoff, durable ingress/outbox and authoritative world publisher/revalidation. Keep private bot features gated.
2. Add shared presentation/action model with explicit action IDs, views, scope, permission, expiry and version. Add Telegram initData verification and restricted session tests; add VK keyboard serializer, verified callback parser and one-use action tests. Never trust platform UI as authorization.
3. Build Telegram Mini App MVP and VK menus over the same private contact/history services. Test link/unlink, stale state, client rendering, duplicate callbacks and no role escalation.
4. Add opt-in community binding and public-only world event subscriptions, admin control, dedicated group ingress/egress, redaction and quotas. Start with one canonical cooperative event type (expedition) and cross-channel join; add guild representation and other mechanics afterwards.
5. Validate actual bots and devices, rate limits, HTTPS reverse proxy, secret/log protection, PostgreSQL concurrency, revocation, privacy, retention and rollback. No automatic enabling, merging or production rollout.

Acceptance: same account and active embodiment across channels; Mini App raw initData forgery/replay denied; VK callback cannot be replayed or borrowed from another user/chat; no inaccessible NPC listed or contacted; unlinked, blocked, stale or ineligible users cannot act; group membership never changes placement; private message and link code never appear in group output; a cross-platform event joins/rewards once; stale admin permissions disable group publishing. Explicit privacy tests should verify that ordinary group text is not collected for NPC memory.

## D. Classic chat RP actions — social, noncanonical
Requested after community design. Reply to another participant's message with an exact Russian or English action (e.g. обнять, /hug, /rp дать пять). Render a caption with both names and a matching anime reaction image/GIF. First catalog: hug, pat, highfive, handshake, wave, dance, poke, cuddle, kiss, slap. No sexual commands. Intimate or aggressive actions require explicit target consent; pending is not a completed action. Ordinary chat RP is optional entertainment in a community, not a world action, NPC message, physical contact, relationship, reward or location change. Default group disabled; separate group verification parser, real same-peer reply, positive human identities, no self/bot target, fresh event, no ordinary chat ingestion. Telegram names are sanitized; VK needs trusted profile lookup; no arbitrary mentions. Group opt-in, participant blocking/opt-out, quotas, durable receipt, consent state/action callbacks and actual send adapter must be implemented before enabling; renderer boolean inputs are trusted server policy, not request parameters. No public endpoints or runtime registration in this increment.

Media: IChatRpMediaSource selects by fixed category only. ApprovedChatRpMedia chooses a random licensed/owned GIF/image from a deployment-owned bounded manifest and exact HTTPS host; attribution preserved. Optional NekosChatRpMedia reference GET uses fixed nekos.best endpoint and verifies exact asset host/category/GIF UUID and attribution; no personal names, arbitrary queries, bulk download, caching or rehosting. Official https://docs.nekos.best/legal/tos.html prohibits commercial use and rehosting; do not enable without explicit noncommercial terms acceptance and checking underlying rights, use licensed/owned catalog for commercial deployment. No actual assets retrieved or attached. For provider delivery prefer approved native attachments / permitted links, not unapproved reuploads; Telegram sendAnimation/sendPhoto and VK approved native attachment mapping follow later. Text fallback if no media. Smoke tests use fixture responses. The accessible GitHub default branches did not contain the historical PHP source; C# legacy VK RP component exists but this is a new implementation, not a direct PHP port.

## E. Group RP runtime (first gated increment)
Explicit deployment configuration Messenger:GroupRp:Enabled (false by default), Groups array with Provider, BotId, Peer, Enabled and Participants numeric ID strings; only approved group + both opted-in participants. Operator must verify current group admin approval, membership and opt-in externally; self-service group authorization, live membership checks and opt-out UI are not implemented. Existing private webhook parser remains first; only explicit group RP reply actions are considered separately. Telegram topic/thread updates are denied until thread-safe routing exists. Sensitive actions (cuddle, kiss, slap) remain blocked until exact target-consent flow is implemented. No account linkage required for ordinary social RP; no game mutation. VK display names remain placeholders until trusted profile lookup.

Durable chat_rp_deliveries table has unique provider/bot/event, pending/sending/sent/uncertain/rejected, two-minute pending TTL and advisory 12/min group cap. Conditional claim elects one send attempt. No replay or automatic retry after provider uncertainty. Terminal records clear participant IDs and caption; schedule Cleanup to clear expired records and delete after two days before production. Pending items left after crash expire; no recovery worker yet. Provider reply flag/token required. Group and participant configuration is checked again before sending, but no atomic provider membership guarantee. Telegram sends approved GIF/PNG/JPG via fixed sendAnimation/sendPhoto URL or text fallback (Messenger:GroupRp:MediaHost and Media entries Category/Url/Attribution); VK sends approved pre-uploaded photo/doc attachment via VkAttachments:<category> or text fallback. No commercial nekos.best use, no arbitrary download/upload. Actual media delivery and VK API response schema need registered-bot staging. No live configuration or credentials committed. CI fixtures cover opt-in, dedup, one claim, redaction, native media request and denial of sensitive actions. No game or server deployment changes.

## F. Interactive RP consent
Sensitive catalog actions now create one durable, two-minute invitation instead of immediately publishing an interaction. Telegram inline callback buttons carry a fixed opaque invitation ID and are acknowledged with answerCallbackQuery; VK inline text buttons use exact rp:a:/rp:d: handles (green accept, red decline). Only the verified target in the exact provider, bot and group can consume the request. Current participant opt-in is checked again, and acceptance atomically consumes the invitation and inserts the delivery; decline/expiry never publishes the action. No new private access or game effects. Duplicate proposals and repeated callbacks cannot create another action. Invitations use one best-effort send attempt, expire after crash, and terminal rows clear participant names/IDs. Advisory six invitations/minute/group; strict multi-node rate limits and current provider membership verification remain deployment requirements. Schedule consent Cleanup alongside RP delivery maintenance. VK text labels are intentionally technical handles pending verified message_event callback support; native callback buttons and user-friendly labels follow. No bot credentials configured, real provider interaction untested, default remains disabled.

## G. Community management
Deployment allowlist remains the maximum permissions; /rp_enable and /rp_disable change a group-local persistent switch only after live provider administrator lookup (Telegram getChatMember, requiring bot admin for management; VK messages.getConversationMembers). /rp_off stores a personal opt-out without requiring role lookup; /rp_on requires live membership and existing operator participant approval. A change never expands the configured group or participant list, so self-service registration of new communities and participants remains pending. Stale/equal timestamp commands are denied. Disabling invalidates pending invitations and queued unsent actions in the same database transaction and clears personal fields. Already-sending network requests cannot be recalled. Effective policy is loaded before queue/claim/send; fresh member lookup for both users before initial action and final send fails closed. The remaining race between provider check, config change and network I/O is not atomic. Membership lookup may add latency and quotas; real provider API/token scope, VK schema, administrator roles, proxy limits and concurrent PostgreSQL tests remain rollout gates. Settings are retained until operator removes them; no original chat text is stored. Fixed public acknowledgements are best effort. No live deployment or credentials.

## H. Custom RP and media collections
Operator-reviewed per-group CustomActions entries under Messenger:GroupRp:Groups use Command (normalized Russian/English alias), Category (existing non-sensitive catalog action), Template (literal caption with exactly one {actor} and one {target}). Example: Command=утешить, Category=hug, Template={actor} утешает участника «{target}». Both /rp утешить and plain утешить in a reply work. Built-in commands retain priority; no sensitive override, arbitrary URL, executable template, free text interpolation or new game actions. Up to 64 definitions; malformed/duplicate custom list disables that group's custom aliases only. Operator reviews template meaning and media rights; this is not a content classifier. Trusted group configuration defines alias scope; runtime policy checks exact definition again before dispatch. Custom captions stored in existing short-lived delivery record. No new DB schema. Self-service editing by chat admins is not enabled yet.

VK native approved attachment collections under Messenger:GroupRp:VkMedia:<category> support up to 256 photo/doc IDs, random selection (duplicates removed), malformed lists fail closed to text; legacy VkAttachments:<category> used when collection absent. Telegram already supports random licensed/owned Media entries per category. No assets committed or external unapproved image fetching. Actual delivery remains gated and requires real bot staging. Smoke covers scope, override rejection, custom caption, stale configuration, duplicate event and approved attachment selection.

## VK native RP callback buttons
Native callbacks use human-readable labels and opaque invitation IDs. Verified message_event scope is provider, community, peer and sender; durable consent checks expiry and exact target. Legacy text handles remain supported. Generic acknowledgement uses messages.sendMessageEventAnswer. Real provider callback shape, subscriptions, scopes and delivery require staging verification. Production remains disabled.

## Telegram Mini App authentication foundation
Dedicated /api/auth/messenger/telegram/mini/exchange, status and logout POST endpoints are disabled unless Messenger:Telegram:MiniApp:Enabled, exact HTTPS Origin, enabled bot configuration and matching AccessToken are configured. Server validates raw initData via official WebAppData HMAC-SHA256, sorted decoded fields, fixed-time hash comparison, duplicate rejection, strict UTF-8 and five-minute freshness (30s future skew); user ID comes only from verified JSON. Signed group context grants nothing. Existing bot:<id> link must predate launch and belong to active account. A canonical proof receipt and hashed random opaque token are inserted together; replay even with reordered fields is denied. Token lives ten minutes and is accepted only in X-Mystic-Mini-Session by dedicated Mini App API, not general Auth JWT or refresh. Resolve rechecks exact linked account and link creation timestamp. Logout revokes but retains receipt; cleanup after two days. Same account relink timestamp is a fence, not distributed atomic revocation. Store token only in JS memory, never URL/localStorage; reopen Mini App to obtain fresh initData after expiry. Status returns only linked/scope/worldAvailable=false. No world data yet, no ordinary account session or character mutation, no browser UI in this increment. Advisory max five active sessions/account, schedule cleanup, protect headers/request bodies from logging, verify PostgreSQL concurrency and real Telegram launch before enabling. Official https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app .

## Telegram Mini App frontend — isolated preview
Shared production frontend build creates a separate Vite entry under Orchestra dist/telegram-mini/index.html, with base /telegram-mini/. No main MysticApp boot, shared account JWT, OAuth, localStorage, sessionStorage or third-party analytics. The official Telegram SDK loads only on this entry. Explicit button exchanges raw initData once; same-origin POST uses credentials:omit, no-store, no redirects, short-lived in-memory capability and dedicated header. Status is checked on connection, visibility return and every 30 seconds while visible; local countdown clears session and logout attempts server revocation. Lost exchange response requires reopening the Mini App, not automatic replay. UI adapts to Telegram color scheme/safe area; reduced-motion support. Linked status only; all game sections are visibly unavailable until trusted world APIs exist. No fabricated character data or game mutations. To stage, configure HTTPS /telegram-mini/ static index/assets separately from SPA fallback, route /api/auth/messenger/telegram/mini/* to Auth, allow only official Telegram SDK script in CSP (verify Telegram Web client embedding policy), suppress sensitive request/header logs, set exact MiniApp Origin, and configure bot menu in Telegram. No route/proxy/bot changes or live deployment here. Build/typecheck and static contract tests are wired into frontend build; real WebView/browser E2E pending. Official SDK: https://core.telegram.org/bots/webapps.

## Soul Mirror read-only profile
Orchestra /api/mini/soul POST accepts the existing restricted capability only, same configured HTTPS Origin and explicit MiniApp:SoulReadEnabled. It resolves via internal Auth /api/auth/messenger/internal/mini/resolve using the existing managed Orchestra device JWT; Auth pins Messenger:Telegram:MiniApp:OrchestraIdentityId, live enabled managed identity, enabled bot, MiniApp:SoulReadEnabled, active account and exact link generation. Fixed internal route and bounded no-redirect client; account ID stays internal. Reads existing SoulEngine record via Get, never Register. Projects only stage, level, rank, XP, available points and canonical GameProgress attributes. No survey, personal memory, assistant card, raw record, account/soul ID or area. Re-resolves immediately before response; not atomic distributed revocation. UI explicitly loads and displays real profile or absent/unavailable, clears on expiry/logout/revocation detection. No placement or NPC availability claim; those need authoritative publisher. Proxy /api/mini/soul to Orchestra only, never expose internal Auth route publicly. Require private HTTPS or same-host loopback for Auth, existing managed credential acquisition must be secured, suppress capability headers/logs, verify HTTP end-to-end, traffic quotas and PostgreSQL before enabling. Default off, no real server changes. Smoke tests read-only canonical progress and no private data.

## Mini App world presence preview
POST /api/mini/presence requires existing pinned Auth capability resolution before and after reading the local WorldPresenceFeed. Disabled unless MiniApp:SoulReadEnabled and MiniApp:PresenceReadEnabled; configure absolute MiniApp:PresenceFeedPath to a private regular file atomically written by the trusted game simulation. Display only own named embodiment/area and permitted named contacts; no entity IDs, action handles or sends. UI expires the view conservatively and clears on visibility changes/logout. No actual simulation writer or VK consumer yet. Internal proxy, OS ACL, real writer and end-to-end verification remain rollout gates.
