# External Identity System — Telegram / VK

Epic [#118](https://github.com/ZeroFantom/MysticEgo/issues/118). This increment is a persistence foundation, not a functioning login or bot integration.

## Model
- Existing Auth UserId remains the only account identifier. `external_identities` stores Provider, Realm, Subject, UserId and LinkedUtc. The primary key prevents assigning a verified subject to two users. A unique index permits one association per account/provider/realm. Separate namespaces avoid collisions between providers or application-scoped IDs.
- Realm is a server-defined identity namespace, not an arbitrary caller-supplied string. Subject is opaque and must be derived from a verified provider assertion. Telegram bot user ID and login subject, or VK user ID and VK ID subject, must not be presumed interchangeable without official protocol validation.
- Additive compatibility DDL runs through AccountSecuritySchema for SQLite/PostgreSQL; no user/password/role/session changes. SQLite fresh/legacy schema and constraints are covered by AuthSmoke; PostgreSQL deployment still requires staging verification.
- ExternalIdentityStore is not registered as a public endpoint. It only persists already verified/confirmed associations and resolves active accounts. It never creates or merges users or issues tokens. Uniqueness constraints protect against conflicting concurrent inserts; later application service must map a failed write to a generic conflict and discard the failed DbContext.

## Before enabling the feature
1. Verify current official Telegram/VK login protocols and subject namespace mapping; configure trusted issuers, client IDs and redirect allowlists server-side. Implement signature/token validation, state, nonce, PKCE where applicable, expiry and replay checks.
2. Bind short-lived single-use link intents to the authenticated account, current session, provider and purpose. Require recent reauthentication and explicit confirmation. Atomically consume proof and persist the link; a failed transaction must never change account ownership. Bot deep-link tokens must be random, hashed at rest and confirmed on both sides.
3. Implement external login using existing Auth session issuance and account checks. For new accounts explicitly handle registration/consent and a secure recovery path, without synthetic usable passwords. Do not accept provider tokens in lieu of Mystic Ego access tokens.
4. Implement unlink/revocation with audit, recent reauthentication, alternative login/recovery checks, session and bot access revocation. Do not enable unlink or external sessions before these protections exist.
5. Add account UI, rate limiting, CSRF protections and provider sandbox integration tests. Do not include real provider secrets in Git. Only then connect messenger identity resolution to authoritative World Presence.

Tests: `dotnet run --project tests/AuthSmoke/AuthSmoke.csproj -c Release`.

## Secure account linking primitives

The new `ExternalLinkIntents` service persists only SHA-256 hashes of 256-bit random, 43-character base64url challenges. The challenge expires in five minutes. It is bound to UserId, active session ID, provider and configured realm. A trusted provider adapter can set a verified subject exactly once. Only the originating account/session may read that candidate or confirm the exact displayed key. Confirmation atomically deletes the intent and persists the association within a serializable database transaction; conflicting ownership is never overwritten. Session/account activity is checked at each phase. Ordinary conflict consumes the challenge; database exceptions roll back. Expired rows can be purged. No production endpoint or DI registration is added.

The service assumes verified provider assertions and recent reauthentication from its caller; it does not implement OAuth/OIDC, callback validation, user consent UI, bot webhook authentication or reauthentication itself. Before activation: rate-limit creation/confirmation, bound storage and schedule cleanup, never log codes or provider tokens, protect callbacks against CSRF, show a human-recognizable verified provider account (not only an opaque subject), verify PostgreSQL concurrency and map storage conflicts to a generic failure. A stolen challenge can stage a candidate but cannot finalize it without the original authenticated session and explicit confirmation; do not auto-confirm. External login and unlink/session revocation are separate gates.

## Provider proof adapters (experimental, no endpoints)

- Telegram: [official OIDC documentation](https://core.telegram.org/bots/telegram-login). Validate RS256 ID token with server-fetched trusted JWKS, issuer, exact single audience, expiry, recent issued-at, expected server nonce, and unambiguous JSON. Use OIDC subject in an app-specific namespace, not the optional Telegram numeric bot user ID. The token exchange, JWKS caching/rotation, PKCE/state persistence and single-use callback are still required.
- VK: [official SDK exchange and userInfo implementation](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts). Prototype exchanges authorization code with PKCE, device ID and state at fixed HTTPS endpoint, then fetches user_info with the access token and checks matching user IDs. No tokens are returned or persisted. Default transport disables redirects. Direct VK documentation was not accessible during design; form-body compatibility, configured domain and response schema require verification with an actual registered VK app before enabling. This is a server-to-server OAuth identity lookup, not JWT signature validation.
- Both adapters assume a server-owned transaction with exact configured client/redirect, fresh one-use state and explicit purpose; never pass browser-supplied configuration or trusted keys. No production endpoint, real provider call, account creation, session issuance or automatic mapping to bot IDs is added. The fixtures use local RSA keys and fake HTTP responses only. Do not enable until integration, threat review and provider sandbox verification are complete.

## OAuth link transaction foundation
ExternalOAuthFlows creates one pending transaction per live link intent. State and independent browser binding are hashed; verifier, nonce and link code are protected with ASP.NET Data Protection using a state-specific purpose. The provider, client, exact redirect and expiry are stored server-side. PKCE S256 is returned to the trusted UI adapter. Callback claims atomically delete the state before a network exchange, require the independent browser binding and active original session, and never issue a session or auto-link. A verified proof can only stage a candidate for the original explicit confirmation. No raw provider secret or OAuth code is persisted.

Before public enablement: server-side allowlisted provider configuration, secure HttpOnly/Secure browser correlation cookie (not a URL parameter), shared encrypted key ring, rate limits, bounded cleanup, recent reauthentication, actual Telegram code exchange/JWKS cache, VK registered app test, provider-specific callback and failure handling, and PostgreSQL concurrency tests. No login transaction for unregistered/anonymous users yet; do not reuse link state for login. Provider code exchange must use only the claimed redirect/verifier/nonce. Losing the key ring or failing the exchange requires starting over. Real provider calls remain disabled.
