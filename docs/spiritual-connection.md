# Духовная связь / Spiritual Connection

Связано с [Epic #118](https://github.com/ZeroFantom/MysticEgo/issues/118). Статус: доменная политика, однопроцессный реестр снимков присутствия и smoke-проверки; не подключено к API, мессенджерам или игровому миру.

## Правила мира

- NPC воспринимает сообщение как духовную связь с игровой сущностью, не как Telegram/VK или работу ИИ. Профили соцсетей, токены и технические метаданные не входят в игровой контекст.
- NPC и игроки без подтверждённой дружбы доступны для общения только в общей текущей игровой области. Другие игроки с подтверждённой дружбой могут общаться в разных областях.
- При перемещении и отзыве дружбы доступ пересчитывается; сохранённая история не является разрешением отправить новое сообщение. Инициатива NPC подчиняется тому же правилу.
- Для первой версии консервативно запрещены связь с NPC вне области, межмировая связь, неизвестная область и NPC↔NPC через этот пользовательский шлюз. Это не запрет внутренних NPC-сцен мира. Возможность связи с NPC-другом, между мирами, с душой без воплощения и точные границы области требуют решения владельца.
- Онлайн-статус не равен местоположению. Офлайн-игрок может иметь серверно подтверждённое размещение. Если такого размещения нет, доступ закрыт.

## Интеграция

1. Auth разрешает проверенный внешний идентификатор в существующий UserId. Отдельно проверяется право на активную игровую сущность; привязка соцсети не даёт право управлять персонажем другого игрока.
2. Авторитетный игровой сервис возвращает согласованный снимок обоих участников (EntityId, WorldId, AreaId, Kind). Для исключения требуется подтверждённая дружба именно этой пары; существующие контакты Collective хранятся на уровне аккаунта, поэтому требуется явное сопоставление. Не принимать эти поля и признак дружбы как утверждение клиента.
3. SpiritualConnectionPolicy.Evaluate возвращает Local, Friend либо Unavailable. Внешний ответ о недоступности должен быть одинаковым для скрытой, неизвестной и запрещённой цели. Политика не является полноценной авторизацией; дополнительно проверяются права, блокировки, согласия и состояние мира.
4. Один прикладной сервис проверяет правила при поиске, отправке, постановке в очередь и повторно перед доставкой/изменением мира. Проверка и запись события должны использовать согласованную версию состояния или транзакцию, чтобы перемещение/отзыв дружбы не создавали окно обхода.
5. Адаптеры Telegram/VK/мобильного клиента не содержат отдельные игровые правила. Общая история, дедупликация, очередь и outbox должны переживать перезапуск. Для NPC формируется контекст игровой личности, памяти и духовного способа общения без транспортных метаданных.
6. Существующие обычные чаты Collective пока не меняются; подключение к новой политике требует отличать внутриигровой чат от аккаунтного общения. Не выдавать публичный API до появления доверенного источника состояния.

## Проверки

`dotnet run --project tests/CollectiveHttpSmoke/CollectiveHttpSmoke.csproj -c Release`

Smoke запускает доменную матрицу отдельно от HTTP. Она проверяет локальность, дружбу, перемещение, потерю дружбы, отсутствующие/невалидные размещения, изоляцию миров, инициативу NPC и запрет обхода NPC через признак дружбы. Это не доказательство готовности транспорта или распределённой доставки.

## Прототип World Presence

`WorldPresenceRegistry` принимает полный снимок от доверенного серверного писателя, а не перемещение из HTTP-запроса. `TryReplace` проверяет уникальность идентификаторов, тип сущности, принадлежность игрока аккаунту и версию ожидаемого снимка. Замена атомарна внутри одного процесса; удаление сущности из нового снимка делает её недоступной. При перезапуске реестр пуст, новая случайная версия не совпадает с предыдущей. `ResolvePlayerPair` читает пару согласованно и проверяет принадлежность отправителя аутентифицированному аккаунту. `RecipientAccountId` нужен исключительно серверному сопоставлению дружбы, не NPC и не клиентскому ответу.

Открытые ограничения: нет источника реальных перемещений, сохранения снимков, межузлового fencing, каталога областей, разрешения активного воплощения и атомарной записи сообщений. `IsCurrent` — только проверка свежести, не транзакционная гарантия. Для NPC-инициативы нужен отдельный доверенный игровой путь, а не подмена игрока. Не регистрировать этот прототип как production-хранилище. Существующая система Collective остаётся неизменной. Следующий этап — интеграционный контракт с настоящим сервером мира, хранилище/версионирование и безопасная проверка дружбы.

## Communication Gateway — reference application service
SpiritualCommunicationGateway is a bounded single-process reference implementation. A trusted world publisher atomically supplies placements, one active embodiment per account, exact directional communication permissions (absence denies), and confirmed mutual player-entity friendships. The caller supplies an independently authenticated account, a request ID, target entity and text only. The gateway resolves the active sender internally; it never accepts client area, sender or friendship assertions. It calls the same SpiritualConnectionPolicy at discovery/reachability, enqueue and commit to the local world inbox. Movement, revocation of permission/friendship and embodiment changes between acceptance and commit deny delivery. A committed in-world envelope contains entity/world IDs, message text, time and spiritual_connection medium only; transport metadata is excluded. Existing Collective account chats are unchanged.

This is NOT persistent messaging or an HTTP endpoint. A single lock gives local atomicity, not cross-node authority. Bounded queue (1024) and dedup records (8192) fail closed at capacity; no automatic eviction or restart recovery. Same account/request ID and content deduplicate acceptance, including previously discarded attempts; acceptance is not delivery status. Committed is a trusted observation for tests, not a public history read. Do not use it to authorize network delivery. Production needs a durable inbox/outbox with delivery status and retention, transactional version/permission checks, authenticated external identity and active-world adapters, block/consent policy, provider revalidation before delivery, and NPC initiative path. Social account friendship must be explicitly resolved to exact active game entities. No assumption that a social login subject equals a bot user ID. Smoke tests cover ownership, locality, friendship, permission, replay, stale state and movement at delivery.

## Local persistent message journal
An optional SpiritualMessageJournal uses a dedicated SQLite file with unique (owner, request), immutable in-world envelope, FIFO sequence and pending/committed/rejected state. The existing gateway can use it instead of its memory queue; acceptance is durable before return. After a restart the gateway refuses processing until a fresh trusted world snapshot is published, and rechecks current active embodiment, area, friendship and permissions before marking an entry committed. Rejected retries cannot enqueue again. The committed record is the local inbox, not actual NPC processing or provider delivery. No live service registration or database path is configured. One process must own the file: no distributed world fencing, no durable identity source check, no network outbox, no retention or at-rest encryption yet. Limit 1024 pending / 8192 total remains fail-closed; operator-managed storage and retention policy needed before rollout. Do not expose the journal to clients. Smoke uses a temporary file, reopens it, checks deduplication, movement rejection and persistence.

## World Communication Bridge (reference, not exposed)
Trusted world snapshots optionally include bounded in-world contact names. Discover filters named entities by current authorization, active embodiment, exact world/area and permissions. Nearby lists local contacts, Friends lists confirmed player friendships including local and remote friends; blocked and unavailable entities are omitted. SendAtRevision checks the selected revision and enqueue under the same lock. A single-process MessengerWorldBridge in Api.Orchestra resolves a verified private bot sender using current DB linkage per command. /nearby and /friends return up to 20 reachable named contacts with random 64-bit selection handles scoped to account/provider/bot/private sender, five-minute expiry, exact world revision; a new list replaces the old one. /talk <handle> <text> resolves that handle and uses the common gateway with a deterministic event-scoped request ID. The local queue is idempotent per account/request and never contains provider identifiers in the in-world envelope. These are internal reference components, not registered for HTTP, DI, MCP or webhook processing. The trusted ingress receipt must still be claimed before dispatch, because reassigning a bot identity can change account namespace. Real world publisher, fresh-state leasing, distributed service identity, transactional receipt/outbox handoff, revocation check before world commit, safe outbound list delivery, provider integration and NPC worker remain required. A committed inbox row is not a delivered NPC reply. No existing Collective chat routing changes. Smoke uses a private fixture sender, synthetic world and local Auth DB, and covers filtered discovery, remote friends, scoped handles, stale revisions, revocation and duplicate enqueue.

## Auth–Orchestra durable transport foundation
With Messenger:WorldTransport:Enabled (default false), authenticated private webhook ingress atomically records the receipt and a bounded world command in Auth DB. Only /nearby, /friends and /talk are queued; no link challenge, operational command or raw update. A command is bound to the active account, exact bot realm/subject and link creation timestamp; an event older than the link is denied. SQLite and PostgreSQL additive schema. A configured live managed identity of kind orchestra with device JWT and exact OrchestraIdentityId may claim at /api/auth/messenger/internal/world/claim, validate, and complete. Generic users/devices denied; no public proxy exposure, body logging or MCP. One conditional lease update elects a worker; 30-second expiry, up to three attempts, stable command ID for downstream idempotency. Validate rechecks current bot configuration, identity ownership/link version, account activity and lease. Terminal acknowledgement clears text, is not proof of actual game delivery. Cleanup clears expired/revoked/exhausted text and removes old rows after retention; schedule and bound maintenance before rollout. Outstanding cap is advisory under concurrent transactions (must enforce quotas in PostgreSQL before enablement). No consumer is registered yet and no replies for queued world commands are sent; use existing disabled defaults. Need authenticated Orchestra client, replay-safe command dispatch, result/outbound delivery and authoritative world publication, plus distributed fencing/revalidation at world commit. Validation is not an atomic cross-service revocation guarantee. Require internal HTTPS/mTLS or equivalent isolated transport, secure database and key/log policy, real concurrency and HTTP integration tests. Local tests use SQLite; PostgreSQL runtime behavior not yet verified. This foundation serves future Telegram Mini App, VK keyboard and community transport without mixing public group data and private game commands.

## World presence read contract
No canonical simulation placement writer exists yet. WorldPresenceFeedReader is a local read-only adapter for a full JSON snapshot from a trusted simulation process, atomically replaced in an OS-restricted directory. Absolute operator path only, regular file <=1 MiB, bounded collections, strict JSON, max age 15s and future skew 2s. Missing, malformed or stale data is unavailable, never cached. Gateway projects owned active embodiment, named area and reachable contacts without raw IDs. This is advisory read only, not a delivery grant. No writer, HTTP upload, UI integration, VK consumer or production enablement in this increment.

## Spiritual dialogue journal foundation
New queue entries pin recipient kind and owning account (player) in both memory and SQLite. Old unpinned records cannot be newly committed or shown in the scoped history. Committed history is read-only, restricted to the currently owned embodiment and exact account, remains after movement. NPC response entry point requires committed player turn, exact owner, same world/area, current both-direction permissions, named NPC, <=2 minute age, and one durable reply per original message. Inference happens outside the gateway lock; CommitNpcReply rechecks current world state. No automatic inference, NPC persona source, HTTP/MCP exposure, production registration, delivery worker or distributed atomicity. Entity IDs must be globally stable and never recycled for NPCs; snapshot freshness remains caller responsibility. Stored text is plaintext in protected SQLite; retention and key management remain prerequisites. Tests cover reassigned recipient, movement, reply dedup, account isolation and restart.

## NPC inference reference adapter
SpiritualNpcDialogue uses the existing WorldAiCluster npc role with includeSharedMemory:false. Input contains only verified NPC name and player speech; model output remains text, not a world command. Trusted caller must supply fresh authorization before and after inference; the gateway also fences on the exact snapshot revision and rechecks current permissions before saving a unique reply. No background consumer or DI registration, no live model call, no persona source or delivery. Model worker access/logging and trusted world publisher remain deployment gates. Snapshot changes during inference conservatively discard output; no automatic retry. A trusted adapter must verify current state rather than use a stale snapshot.

## NPC personality and scoped dialogue recall
Trusted SpiritualWorldSnapshot optionally carries NpcProfiles keyed by exact NPC entity ID, with Personality (500 chars), SpeechStyle (160), up to eight approved KnownFacts (240 each) and RecallDialogue (default false). Profiles must refer to named NPC placements; invalid/duplicate/player profiles are rejected atomically. Profiles are copied into the snapshot revision; public presence does not expose them. WorldAI reference adapter now requires an approved profile, excludes global memory and passes only character, approved knowledge, current speech and optional prior completed dialogue for the exact account + embodiment + world + NPC. Recall selects up to six earlier completed exchanges, bounds each speech to 400 chars, excludes later replies and drops oldest context to fit the 5000-character model request. Dialogue is untrusted speech, not canonical facts or instructions; no tools or world mutations. No automatic generated summaries, cross-player memory, relationship scores, profile authoring UI or live simulation publisher. Profile updates invalidate pending inference via revision fence. Single-process reference only; stable unrecycled NPC/embodiment IDs, UTC timestamps, data retention, player-facing consent and worker authorization must be addressed before production. No actual inference or deployment in this increment.

## Durable world authority contract
WorldAuthorityStore is an internal single-process/local SQLite publication contract for the future canonical simulation writer. Trusted writer initializes storage and publishes complete coherent snapshots with expected monotonic revision; transaction validates and pins entity ID to world, kind and owner, retires omitted IDs permanently, rejects stale writers, reassignment or retired identity reuse. Movement is a full snapshot update, not a client request. Absence means retirement, not streaming/unload; cross-world transfer requires a new entity ID. Bounded lifetime registry (65536), bounded 1 MiB payload, no automatic refresh of stale snapshots. ReadCurrent is read-only and never creates storage. Set WorldAuthority:DatabasePath in Orchestra to select this source for both Mini App and messenger discovery, without fallback on failure; unset uses existing legacy feed. Private OS ACL, single trusted simulation writer, trusted local clock, backup/restore and retention policy are required. No HTTP publication, automatic simulation, real game movements, registered dialogue runtime or production enablement. Smoke exercises restart, CAS, movement, owner fencing, retirement and expiry. Snapshot read is not an atomic delivery authorization.

## World Simulation Core
Internal deterministic event batch reducer over the durable authority store. Trusted operator supplies directed topology and a caller authorized to issue spawn player/NPC, move on a directed passage, select/deactivate owned embodiment, retire entity, directional grant and confirmed friendship events. One batch (1–64 events) validates and commits with expected revision; invalid batches never partially publish. NPC profile is supplied on spawn and validated by the snapshot gateway. Retirement clears permissions, friendships, labels, profile and active selection; permanent lifetime fence prevents reuse. Deactivation preserves placement, not retirement. No automatic proximity grants, no raw user or model commands, no cross-world movement, no autonomous simulation/tick, topology persistence or external event producer. Caller must authenticate game events and enforce gameplay conditions such as locks, combat, consent and friendship authority. No HTTP/MCP endpoint, DI registration or production change. Tests cover spawn, directed movement, atomic rollback, ownership, revocation, retirement, restart and read projection.

## World Simulation Host
Opt-in Orchestra WorldSimulation:Enabled registration, absolute WorldAuthority:DatabasePath, trusted WorldSimulation:Areas and Passages configuration. Internal bounded volatile queue (128 batches, up to 64 events each, 16 batches per cycle); trusted in-process callers submit expected revision, await durable application result. No HTTP/MCP or external event producer. One logical tick per 3-second host cycle while it owns a successfully applied revision; tick persisted in the same SQLite payload without changing gameplay revision, no offline catch-up. Atomic state changes preserve logical time. Startup never renews an existing snapshot without an authorized batch; stale snapshot, storage error or competing state revision stops heartbeat. One host per private DB is an operational requirement, not distributed leader election. Stop drains pending callers as unavailable; in-flight response uncertainty requires reconciliation, not replay. Queue not durable; no actual game event source, autonomous NPC AI, scheduled gameplay or production activation. Smoke tests host lifecycle, persistent ticks, revision separation and restart fail-closed.

## NPC autonomous routines
Optional WorldSimulation:NpcRoutinesEnabled (default false), inside enabled WorldSimulation host. Operator config WorldSimulation:NpcRoutines lists exact EntityId, WorldId, PeriodTicks (1..1000000 logical ticks), Stops (FromTick starting at 0, AreaId, Activity). At most 64 NPCs and 32 phases per NPC. Planner ignores absent entities and players, chooses shortest directed path with ordinal tie-breaking and emits at most one MoveWorldEntity per NPC per tick. No teleport, respawn, permission changes, economy or automatic dialogue. Activity is descriptive intent, not actual work/rest mechanics. Host only runs routines after a successful authorized batch and fresh heartbeat; atomic core CAS publishes actual moves, and failure disarms heartbeat. No catch-up after downtime. Config topology and schedules are trusted operator input, not model output. Smoke tests phase transitions, directed paths, missing/retired entities, player exclusion and durable movement. Actual gameplay producers, live runtime, time-of-day UI and NPC initiative are not enabled by this increment.
