# Инфраструктура MysticEgo

Установщик рассчитан на Linux VPS с Ubuntu 24.04 LTS. CloudDesk использует
свой SSH-мастер и запускает команды от root на выбранной машине. Откройте
**Обновление узлов → Развёртывание инфраструктуры**. Можно выбрать VPS
Timeweb или ввести SSH-адрес другого провайдера.

## Мониторинг

- **На VPS Orchestra.** Выберите **Prometheus и Grafana**. Оставьте
  HTTPS-адрес пустым. Prometheus читает локальный `127.0.0.1:5500/metrics`.
- **На отдельном VPS.** Создайте ключ командой `openssl rand -hex 32`.
  На VPS Orchestra выберите **Источник метрик Orchestra** и введите ключ.
  На целевом VPS выберите **Prometheus и Grafana**, укажите HTTPS-адрес
  Orchestra и тот же ключ. Установщик проверит выдачу метрик до создания
  контейнеров.

Docker и Compose v2 устанавливаются при необходимости. По умолчанию
Prometheus собирает метрики каждые 15 секунд и хранит их 15 дней. Grafana
получает источник MysticEgo и готовый дашборд. Контейнеры используют
постоянные тома. Порты 9090 и 3000 слушают только loopback.

```bash
ssh -NT -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 admin@monitoring-vps
```

Откройте `http://127.0.0.1:3000`. Имя пользователя `admin`, начальный
пароль на хосте в `/opt/mysticego-infrastructure/monitoring/grafana-password`.
Если Grafana уже использовала тот же том, действует прежний пароль.
В Prometheus откройте `/targets`, чтобы проверить состояние сбора.

## Установка из Orchestra

На каждом целевом VPS один раз запустите **Подготовить управление из
Orchestra** через CloudDesk. Это помещает фиксированный установщик в
`/opt/mysticego-infrastructure/runner`. Создайте отдельный ключ Orchestra
и добавьте его публичную часть в root `authorized_keys` на каждом
целевом VPS с ограничением только на запуск установщика:

```text
restrict,command="/opt/mysticego-infrastructure/runner/run-web.sh" ssh-ed25519 <публичный ключ>
```

Укажите абсолютные пути в окружении Orchestra. Ключ и файл known_hosts
должны быть доступны пользователю `mysticego`. Проверьте SSH-отпечатки
серверов по независимому каналу. Для контейнерной установки храните их
в уже примонтированном каталоге состояния и убедитесь, что в контейнере есть
клиент OpenSSH.

```text
InfrastructureSetup__IdentityFile=/var/lib/mysticego/infra-ssh/id_ed25519
InfrastructureSetup__KnownHostsFile=/var/lib/mysticego/infra-ssh/known_hosts
InfrastructureSetup__Targets__Orchestra__Host=127.0.0.1
InfrastructureSetup__Targets__Orchestra__Port=22
InfrastructureSetup__Targets__Monitoring__Host=monitoring.example.net
InfrastructureSetup__Targets__Monitoring__Port=22
```

На штатном сервере добавьте переменные в `/etc/mysticego/orchestra.env`
и перезапустите службу. Затем откройте **Диагностика → Развёртывание
инфраструктуры**. Серверы выбираются из настроенного списка. Операции
подтверждает главный разработчик.

## LM Studio

Выберите **LM Studio и модель** на целевом VPS. Профиль мира загружает
Qwen3 4B, профиль панелей — Qwen3 1.7B, оба в GGUF Q4_K_M.
Один управляемый процесс llmster на хост загружает выбранный профиль.
API слушает `127.0.0.1:1234`. Размер памяти зависит от модели и
выбранного контекста. Модели проверяются через `/v1/models`.

Если модель на другом VPS, поднимите на VPS Orchestra постоянный SSH-туннель
с проверкой ключа сервера, например с привязкой к `127.0.0.1:11234` и
пробросом на `127.0.0.1:1234` сервера модели. Затем на VPS Orchestra
выберите **Подключить модель к Orchestra**, укажите профиль и адрес туннеля.
Панель проверяет модель и перезапускает Orchestra с новым назначением.
Туннель должен работать и после перезагрузки обоих VPS.

Файлы GGUF хранятся в `/var/lib/mysticego-lm/.lmstudio/models`. Для переноса
скопируйте каталог вместе со структурой издатель/модель и назначьте владельца
`mysticego-lm` на целевой машине. Также можно импортировать отдельный GGUF
через `lms import --copy --user-repo издатель/модель файл.gguf` после установки CLI.
Сохраните исходный файл до проверки, что модель загрузилась на новом VPS.

## SQLite и PostgreSQL

По умолчанию Auth и каждая панель используют SQLite в своём каталоге данных.
Новый общий адаптер поддерживает PostgreSQL для записей панелей и журнала действий
Orchestra, Global, Local, Agent и Audit. Auth использует существующий EF Core/Npgsql.
Файловые хранилища (аватары, ресурсы, WorldAI jobs.json и другие файлы) не перенесены в SQL.
Не используйте одну базу роли для нескольких независимых экземпляров: каждому узлу
нужна отдельная база/роль, даже если сервер PostgreSQL общий.

### Новая Orchestra: в CloudDesk → Инфраструктура → Развернуть узел

Независимые параметры:
- Способ запуска панели: systemd (обычный) или Docker.
- Хранилище: SQLite (по умолчанию), PostgreSQL на этом VPS через systemd, PostgreSQL на этом VPS в Docker либо заранее подготовленное подключение.

Для same-VPS PostgreSQL установка выполняется до первого запуска Auth/Orchestra, с отдельными случайными паролями. PostgreSQL 16 из Ubuntu 24.04 (обычный выделенный кластер 16/mysticego) или PostgreSQL 17 Docker с постоянным томом. Оба используют 127.0.0.1:55432 по умолчанию. Docker панели использует host network и тот же loopback. Установка не меняет существующий PostgreSQL-кластер main, не удаляет тома и не преобразует один способ установки в другой. Ubuntu может создать стандартный кластер main при установке пакета.

### База на отдельном VPS

В CloudDesk → Обновление узлов → Развёртывание инфраструктуры:
1. Выберите VPS базы и PostgreSQL (обычная установка или Docker).
2. Для защищённой VPN укажите частный IPv4 и разрешённый CIDR /24–/32 (лучше адрес клиента /32). Установщик не поднимает VPN сам. Альтернатива — постоянный SSH-туннель до loopback:55432 с проверкой ключа SSH.
3. Получите пароль каждой роли на VPS базы из root-only /opt/mysticego-infrastructure/postgres/credentials.json; не отправляйте его в чат или журнал.
4. На **будущем VPS панели** выберите «Подготовить подключение новой панели к PostgreSQL». Для Orchestra выполните отдельно для Auth и Orchestra. Укажите IPv4 базы в VPN (подтвердите защищённую сеть) либо 127.0.0.1 для уже работающего туннеля. Пароль выбранной роли обязателен для удалённого сервера. Проверяются соединение и пустая база. Подключение хранится в root-only /etc/mysticego/database-staging.
5. При первом развёртывании Orchestra выберите «заранее подготовленное подключение». Файлы переносятся в /var/lib/mysticego с правами 0600 пользователя mysticego.

Не открывайте порт 55432 в интернет. Автоматический сценарий использует SSL Mode=Disable только для loopback или явно подтверждённой защищённой сети; это не самостоятельная TLS-защита. Для внешнего управляемого PostgreSQL вручную используйте Npgsql connection string с SSL Mode=VerifyFull, проверяемым CA и отдельной базой/ролью.

### Остальные панели / самостоятельные сервисы

У нового узла настройте Node__DatabaseConnectionFile (абсолютный путь к файлу с Npgsql connection string) или Node__DatabaseConnection. Не задавайте оба. Для LabHost положите файл <role>-postgres.connection в корень данных узла до запуска; для native installer — в его output/data. Для контейнера примонтируйте файл только для чтения и настройте переменную окружения. Node__DataPath продолжает задавать локальную папку файлов и маркера провайдера. Auth по-прежнему использует Authorization__ConnectionString или auth-postgres.connection в LabHost. Автоматическое первоначальное развёртывание Global/Local/Agent/Audit из CloudDesk не добавлено; их SQL-адаптер доступен при ручной настройке нового узла.

### Существующие установки

Установка отдельной СУБД не переключает работающую панель. Переключение с существующего SQLite запрещено до явной миграции. Не удаляйте SQLite, WAL, конфигурацию, базы или ключи ради обхода проверки. Маркер PostgreSQL не позволяет автоматически откатиться на пустой SQLite при потере настройки. Перенос существующих данных, проверка резервных копий, репликация и высокая доступность — отдельные задачи. Прежний пункт Auth PostgreSQL сохранён для совместимости, для нового центра предпочтителен новый сценарий.
